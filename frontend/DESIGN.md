# Design System

### Product photos

Product forms use one controlled photo field with a visible label and one large, pale upload area with a dashed border, centered camera icon, direct instruction, and JPG/PNG/WebP helper text. The complete area is the upload target; after selection, preview, filename, replace affordance, and an icon-only remove action remain within that same stable area. Empty and preview states crossfade in that stable frame: the old state exits over 120ms while scaling to `0.98`, and the new state enters over 180ms from the same scale. Reduced-motion contexts retain a 120ms opacity handoff without scale. The field accepts one photo up to 5 MB and the backend automatically compresses it to a maximum stored size of 200 KB. Stored product photos are normalized to JPEG, use a white background for transparent source pixels, and keep their aspect ratio while quality and dimensions are reduced as needed. Do not show a category stock photo before the user chooses an image, and do not add a second filename caption below the field. Product-list rows place an 80px rounded thumbnail at inline-end, opposite the product identity and operational values; images remain decorative when adjacent text already names the product. Category fallback photography is allowed only when a product has no stored image URL. Owned product photos are delivered through the app's first-party `/api/v1/product-images/` route, which reads authenticated R2 objects and returns immutable browser caching; production UI must not depend directly on the rate-limited `r2.dev` development endpoint. If a stored image fails during browser startup, keep a neutral placeholder while retrying the same URL after 500ms, 1.5s, and 3s; never substitute unrelated category photography. Connectivity, page visibility, and mobile browser resume events retry the original stored URL again, using a cache-busting query without changing the persisted URL. A permanently broken stored URL settles on the neutral placeholder. Product-form barcode capture keeps manual entry and a separate 36px icon-only `Pindai barcode` action in one labeled row with an 8px gap. The scan action follows the input, exposes an accessible name, and retains the shared 10px control radius.
In the product editor, photo is an optional secondary field after the operational fields (`Barcode`, `Kategori`, `Harga`, `Stok`, and `Satuan`) so repeated setup stays fast; keep the upload surface itself large and stable.

### Product variants

Product variants are one atomic product-editing workflow, not a sequence of independent mutations. `Tambah produk` and `Ubah produk` use dedicated private routes (`/products/new` and `/products/:id/edit`) for one stable full-page workspace containing both `Informasi produk` and `Atur variasi`; they never open a product or variant modal over the product list. The app shell preserves Produk as the route context but enters an immersive mode that hides the global top bar and bottom navigation, preventing duplicate headers and overlapping actions while keeping the editor component mounted across guarded navigation. A named `Kembali ke daftar produk` control leads the sticky page header, while the in-editor step action is labeled `Kembali ke informasi` so the two destinations remain distinct. The centered page title remains visually uppercase with `0.14em` tracking, but the page title, current-section heading, variant section headings, and mobile variation name all use the same compact 14px operational size; weight, tracking, placement, and supporting copy provide hierarchy without competing scales. Do not render a step indicator or `Langkah N dari 2` label; the section heading and contextual actions provide wayfinding. Only the central body scrolls. On the information step, the product-mode status pairs directly with its action: a product without variants explains that it uses one price and stock, while `Tambah variasi` opens an empty variant workspace without mutating the draft; the first attribute is created only through an explicit `Tambah atribut` action. When variants exist, the status explains that price, stock, and barcode follow each combination and `Atur variasi` reopens that editor. This status action uses the shared `sm` button scale and keeps its label on one line. The sticky safe-area-aware footer owns step navigation and `Simpan`, keeps progress inside the primary action, and prevents duplicate submission. Leaving a changed draft replaces the central page content with `Buang perubahan?` without stacking another surface; continuing returns focus to the current step. Browser Back and reload are protected while the draft is dirty. Saving sends the parent fields, complete `attributesConfig`, and complete variant matrix in one transaction, and a failed save preserves the draft and previous server state.

New product drafts leave `Kategori` and `Satuan` empty until the user chooses them instead of silently selecting the first master-data item. The first editor focus lands on `Nama`; changing steps focuses the current section heading. Product fields validate on blur after they are touched, and the first submit validates the complete draft, moves to the affected step, opens the affected mobile variant row, and focuses the first visible invalid field. Save failures remain visible in the sticky footer until the next correction or successful save, with Indonesian user-facing validation copy.

Attributes use flat divided sections rather than nested cards. Each section has `Nama atribut`, a structured wrapping token field, and a 44px contextual action menu for rename, duplicate, reorder, and destructive removal. The token field follows the standard text-field hitbox and surface height when empty, expands only when tokens wrap, and keeps a trailing Enter affordance visible; activating that affordance commits the same draft as the Enter key. Token chips use a compact 28px visual height inside the 36px field surface so their nested border never competes with or stretches the input; icon-only removal retains a 44px effective vertical hit area without changing the chip silhouette. Enter or comma commits a trimmed token; empty and case-insensitive duplicates are rejected inline. Tokens support individual edit/removal, Backspace/Delete, Arrow navigation, stable focus, long wrapping values, and visible focus. Removing an attribute uses an in-place, specific confirmation because it can discard row-level price, stock, and barcode data; the confirmation uses a borderless danger-soft surface and `sm` actions. `Tambah atribut` is a labeled `sm` full-pill action with a 2.8px rounded plus stroke. Collection edges own the outer rules, rows own internal dividers, and empty states never add a nested border; variant-table header cells likewise own their bottom divider without a second wrapper line.

The Cartesian matrix preserves stable server IDs plus draft-only row identities, and keeps operational values for compatible combinations. Expanding a stocked simple product transfers stock to only one reused row; every new combination starts at zero. Collapsing an attribute sums stock for combinations that merge. Structural edits show the actual `N variasi · N dijual` state and, for multiple attributes, the multiplication formula. The editor caps the matrix at 100 combinations, keeps scroll/focus stable, and exposes a neutral temporary status with `Urungkan`; Command/Ctrl+Z applies when focus is not inside a text editor.

Desktop and sufficiently wide tablet layouts use one semantic, compact table with a shared sticky header: `Variasi`, `Harga`, `Stok`, `Barcode (opsional)`, and `Dijual`. Rows use dividers, tabular numeric figures, stable keys, persistent `Rp` prefixes, inline field errors, 44px scan actions, and combination-specific switch names. Mobile replaces the table with disclosure rows showing name, sale status, price, and stock; selecting a row expands its editable fields inline directly beneath the summary and collapses the previously open row. The trigger remains visible, exposes `aria-expanded` and `aria-controls`, and the panel is a named region. Do not navigate to a separate mobile detail state, horizontally scroll form fields, or animate frequent keyboard-triggered disclosure changes. At 200% zoom the layout is allowed to adapt to this mobile pattern.

`Edit massal` separates full-pill `Atur harga`, `Atur stok`, and `Ubah status` actions. Each focused popover states how many variations it affects; empty values never erase data, and one bulk field never mutates another. Status offers `Aktifkan semua` and `Nonaktifkan semua` without confirmation because Undo is available. In mobile variation detail, show concise visual labels `Harga`, `Stok`, and `Barcode (opsional)` because the variation name already supplies context, while each input and scan action retains the complete variation-specific accessible name. Field-adjacent scan actions share the field hitbox row without margin offsets, and the `Dijual` row has no decorative top border. A sold variation requires a positive price; every stock value is an explicit non-negative integer. Optional barcodes remain unique across the parent, sibling variations, and other products, with both conflicting rows named inline. Submit validation moves to the correct step, opens the affected mobile row, scrolls and focuses the first visible invalid field, and respects reduced motion. Clearing a corrected field removes empty row-error metadata; mobile disclosure and focus recovery run only for an explicit submit-validation request, never on each keystroke. All menus, tokens, popovers, table controls, and navigation remain keyboard-operable with semantic labels and visible focus.
Destructive attribute confirmation replaces the affected attribute fields in the same layout slot using a crossfade, announces the data loss, moves focus to `Batal`, and returns focus to the nearest remaining attribute action (or `Tambah atribut`) after confirmation. Attribute and bulk popovers use matching origin-aware enter/exit scale and opacity transitions; closing commits immediately and never waits for an animation. Reduced-motion removes spatial transforms, while reduced-transparency makes editor chrome, sticky headers, and Undo status surfaces opaque.

Product lists summarize configured variants as `N variasi · total stock unit`; a transparent default variant never creates an empty chip. Parent and variant barcodes stay unique against active and inactive records so client validation matches database constraints; a historical variant removed from the matrix releases its barcode when it is logically deactivated. Parent and variant barcode fields both pair manual entry with the same local scan action; a variant scan writes only to the targeted matrix row. At the cashier, configured products remain one catalog card. The selector uses one 44px-or-taller pressed-state option per attribute, disables combinations that are inactive, unavailable, or exhausted after cart quantities are deducted, and reports the exact selected price and remaining stock in a polite status region. It relies on the containing dialog's one title and one dismissal action. Scanning or searching an active variant barcode resolves directly to that variant, and a failed add keeps the selector open so the user can recover without losing context.

Stock is variant-scoped whenever a product exposes variants. Manual movements require a variant selection, preview that variant's current and resulting stock, submit `variantId`, and show variant attributes in low-stock alerts and movement history. Checkout and stock responses identify both `productId` and `variantId` so local nested stock can reconcile without mutating unrelated parent or sibling values.

### Master data

Settings uses query-backed navigation for `profile`, `categories`, and `units`. Its workspace keeps the smartphone composition at every width: navigation remains an overflow-safe horizontal tab row and the active surface stays centered with a 48rem maximum width. Tabs and actions keep targets at least 44px tall; long master-data names wrap inside `min-width: 0` identity groups, and item, confirmation, restore, create, and save actions remain stacked and full-width. Selection uses a neutral muted surface and `aria-current="page"`, never the primary action treatment. Do not add a vertical navigation rail or redundant store-summary aside. Settled tab content uses a short direction-aware 20px slide-in that follows `profile → categories → units`; it has no exit delay, remains interruptible, skips the first render, and becomes a brief opacity-only crossfade under reduced motion.

The Profile form keeps adjacent fields in 8px groups and separates the tax and device-preference sections with a 16px rhythm. Switch rows use at least a 44px interaction height; their copy may shrink on narrow screens while the switch track stays at its intended size. The save action is text-only so the primary label remains the visual anchor. The enabled `Bunyi pemindaian` switch uses the success-green control tone, while disabled state remains neutral.

Master-data lists use one primary bordered surface with flat rows and quiet dividers; never wrap each row in another decorative card. Active status is implicit in the main list, while low-frequency rename and archive actions live in one trailing overflow menu. Archiving is reversible and should complete immediately with an `Urungkan` toast rather than expanding a confirmation card; no master-data flow hard-deletes records. Archived items stay behind a compact disclosure row and use the same flat row rhythm at lower emphasis. Inline master-data inputs and the `Tambah`, `Batal`, and `Simpan` buttons use the `sm` button scale, full-width stacked actions, and 44px interaction targets. Finite product selectors keep search, selection, and a quiet `Tambah … baru` action inside one anchored popover; activating create replaces the option list with a compact input and secondary text actions. A successful create selects the new item and closes only the popover, while an archived-name match offers `Pulihkan` inline. Current archived values remain visible but cannot be newly assigned, and category/unit lists stay alphabetical. The master-data manager is the primary bordered surface and must not be wrapped in another decorative panel.

## Product Surface

Wipay is a retail point-of-sale surface for Indonesian UMKM shops. The interface should stay simple, dense, quiet, and fast for repeated cashier work: white surfaces, soft borders, compact controls, product-image cards, clear stock signals, and near-black primary checkout actions.

### Brand identity

The favicon is the compact brand mark: an abstract isometric retail volume made from exactly three uninterrupted architectural planes inside an edge-to-edge 32px square with an 8px corner radius. The isometric volume spans 22px horizontally with a 4–5px optical inset so it remains prominent after browser-tab padding is applied. Keep `public/favicon.svg` as the active browser favicon so it remains crisp at tab sizes. The volume contains no door, window, letterform, or text and stays intentionally restrained—no gradient, shadow, border, literal shopping symbol, or fine detail. `favicon-soft.svg` and `favicon-inverse.svg` are approved tonal explorations of the same geometry; variants may change only the neutral plane and background colors, never the silhouette, coordinates, scale, or number of planes. The mark complements the shared `Wipay` wordmark but does not replace it in application headers.

## Tokens

Color tokens live in `src/index.css` through Tailwind v4 `@theme`: `app-bg`, `surface`, `surface-muted`, `border`, `text`, `text-muted`, `accent`, `danger`, `success`, `warning`, and `focus`.

The global `app-bg` canvas is pure white and matches `surface` on every public and authenticated page. Do not use gray page bands or alternate section backgrounds to create hierarchy. Use spacing, typography, complete component borders, and semantic status fills instead. Page headers, local toolbars, navigation chrome, content sections, list rows, and card internals do not use standalone top or bottom divider lines; a complete border may still define an input, card, table, drawer, popover, or dialog. One deliberate exception: the landing footer's status line sits above a quiet full-width top border so the copyright row reads as a closed strip.

Where older component descriptions below mention quiet, inset, or cell dividers, interpret that relationship as spacing and alignment only. The divider-free global rule above is authoritative, with one deliberate exception: the Products list uses a quiet full-width divider between adjacent rows to keep dense catalog items visually distinct.

`text-subtle` remains an accessible neutral rather than low-contrast decoration. Text carrying meaning must meet at least a 4.5:1 contrast ratio at normal sizes; use borders, spacing, or weight—not barely visible gray—to preserve hierarchy.

Typography uses Quicksand through `--font-sans` for headings, product names, labels, search, categories, units, status pills, helper copy, and actions. JetBrains Mono through `--font-mono` is a restrained operational-data accent, not a second body face: apply it only to barcodes, prices, stock numbers, totals, deltas, and their editable input values, always with tabular figures where numeric comparison matters. Keep adjacent language such as category names and units in Quicksand, and never apply Mono to a complete row, form, drawer, or paragraph. Operational text should stay between 12px and 17px. Small barcodes may use 12px Mono with slight positive tracking; page titles use the established 18px authenticated top-bar treatment.

Spacing follows 4px-based Tailwind steps. Repeated panels use 24px gutters and cards use 12px to 16px internal padding. The control contract applies at every viewport width: standard text buttons use a 48px visual and interaction height, while inputs, dropdowns, and search fields use 44px; compact controls may use a 36px visual surface only inside a 44px interaction target. Icon-only controls retain an 18px to 20px icon inside the same 44px target, and adjacent targets keep at least 8px separation. Textareas start at a 96px minimum height and grow with content. All forms use exactly 8px between adjacent field groups and inside paired numeric or variant-field grids; larger gaps remain reserved for separation between non-form sections. Editable inputs, textareas, and native selects use at least 16px text on coarse touch devices to prevent focus-triggered browser zoom; never disable user pinch-zoom through viewport restrictions.

Radius follows an 12px/10px/16px/32px base hierarchy: standard text buttons use full-pill radius for the friendly primary action language; `button` is 12px for compact option and utility rows; `control` is 10px for inputs, selects, and icon utility controls; `card` and `panel` are 16px for cards and panels; `overlay` is 32px for modal surfaces and drawer-facing corners. Use standard CSS `border-radius` geometry consistently across browsers; do not apply `corner-shape`, superellipse, corner smoothing, masks, or path-based corner overrides. Modal and drawer headers use the shared sticky-header contract so the title and dismissal actions remain visible while only the body content scrolls. Dialog surfaces separate the opaque header, scrollable body, and opaque footer into distinct flex regions; modal titles keep 16px of space before the header's lower boundary, and scrolled controls must never paint through or around the header. Full-radius circles, avatars, pills, progress tracks, and handles remain fully circular. Do not introduce additional radius tiers unless a component's geometry explicitly requires an exception.

Shadows are reserved for content surfaces: `low` for cards, `panel` for elevated overlays and interior panels, and none for buttons or selected control states. The outer app shell and top bar stay shadow-free; the floating bottom navigation is the sole chrome exception and uses the soft, downward `--shadow-navigation` token to separate its translucent material from content moving beneath it.

Every button follows one Family-influenced flat system. Primary uses a solid near-black surface with white text; secondary uses a neutral surface and quiet border; ghost uses transparent chrome with text and hover fill; danger uses the semantic soft-red surface. Button typography follows the control size: `xs` is 12px, `sm` is 14px, `base`/`md` is 16px, `lg` is 18px, and `xl` is 20px, all semibold. Standard text buttons use a full-pill radius and 24px line-height at 16px; large actions use 18px type, while compact utility buttons use 14px type and retain their smaller control radius and hit-area contract. Tracking tightens slightly as button type grows so labels stay optically balanced. Form and dialog action groups use the shared `form-actions` pattern: one action fills the row, while two actions become equal-width side-by-side columns with an 8px gap. The POS product-card add action is the intentional visual exception: it uses a white circular plus control over the product photo so the repeated action remains compact and spatially attached to the item without adding another strong color. Buttons and selected control states never use gradients, bevels, pseudo-element rings, text shadows, or elevation shadows; the repeated photo-overlay add control alone may use `shadow-low` to remain legible over changing imagery. Hover changes only semantic background or text color. Press feedback scales to `0.97` over the shared interaction duration, keyboard focus retains the two-pixel focus outline, disabled controls retain reduced opacity, and reduced-motion contexts remove the transform.

Motion uses `--duration-fast`, `--duration-base`, and `--ease-standard`. Keep transitions short and functional. Transition only explicit, compositor-friendly properties such as transform and opacity; do not animate box shadows. Gate hover motion behind `(hover: hover) and (pointer: fine)`. Dialogs enter and exit over 200ms with backdrop opacity plus a centered surface scale from `0.98` to `1`; in reduced-motion contexts, remove the scale while retaining the opacity transition. Modal dialogs, bottom drawers, and the overlay cart share one frosted-glass scrim: a translucent white veil with 4px backdrop blur and restrained saturation. The material keeps the workspace recognizable while separating it from the opaque active surface; reduced-transparency contexts replace the effect with an opaque neutral veil and no backdrop filter. Presenting a modal, bottom drawer, or overlay cart scales only its underlying content to `0.985` over 220ms, leaving the scrim and active surface at full scale; stacked layers retain this depth separation until each layer exits. Reduced-motion contexts remove the underlay transform rather than replacing it with another spatial effect. The barcode scanner is not a dialog: it takes over the full viewport and should transition with opacity only, without a floating-card scale or inset reveal. Add-to-cart actions should respond on press and confirm completion with a brief product-card pulse or compact status chip, using transform and opacity so the workflow stays fast. Async form labels may use the shared directional text swap: old text exits upward by 4px over 120ms and new text enters from 4px below over 180ms, while the parent control retains a stable minimum width. Reduced motion keeps only the 120ms opacity handoff.

Anchored popovers use the shared floating portal layer above dialogs and recalculate their viewport position on resize or scroll. They may flip above the source control when vertical room is limited, and must never be clipped by a dialog's scroll container.

Loading skeletons should mirror the final retail layout instead of showing generic bars alone. Use full-page skeletons only before a page has initial data. Once settled content exists, refetches and filter loads preserve the current layout, contrast, and usable controls without a visible badge, pulse, or opacity change. Announce background activity through the shared visually hidden polite status region; surface only errors or explicit mutation progress. Disable controls only for explicit pending mutations such as save, checkout, or destructive confirmation, not for background refetches. For POS surfaces, reveal initial skeleton cards and order-summary blocks with a short 560ms rise-in and a looping horizontal sheen that travels across each placeholder in roughly 1.5s. Apply the same motion language to dashboard cards, catalog tables, transaction lists, and settings forms so every initial data load feels consistent. Keep the shimmer subtle, use surface-muted tones plus a soft white highlight, and disable both the rise and shimmer in reduced-motion contexts. The Settings initial skeleton uses the same compact horizontal navigation and centered 48rem content geometry as the settled page; it never introduces a desktop rail or restores the removed store-summary aside.

Operational tables on Produk, Stok, and Transaksi begin directly with the column-header row inside their bordered surface; do not add a second card header that repeats the page title or explains sorting. Keep search, filters, and creation actions in the page toolbar; background updating status stays visually hidden. Header labels and body values share the same horizontal cell inset, including sortable headers, so every column starts or ends on one consistent alignment line. The table wrapper has no horizontal padding: header and row separators must run edge to edge across the bordered surface on all three pages.

The Produk page keeps sorting, category, and status controls together inside its icon-only Vaul bottom drawer; do not add a separate sort icon. The search toolbar contains only search and the product-creation action, and it does not render a persistent category-pill row beneath it. The drawer presents `Urutkan` first, followed by category and status. Sort choices use direct task labels rather than a separate field-and-direction pair: newest, oldest, name A–Z/Z–A, lowest/highest stock, and lowest/highest price. `Terbaru ditambahkan` is the default. Drawer selections remain local drafts until `Terapkan` commits all three controls in one update and closes the sheet. Closing through X, scrim, Escape, or swipe discards drafts; reopening restores the last applied values. `Atur ulang` resets only the drafts to default and still requires `Terapkan`, while page search remains live and debounced. Its header contains only the `Filter produk` title and close action, without subtitle copy. Match the product modal optically: use 24px surface insets and title-to-content separation, 16px between filter groups, 8px between each field label and its options, and 24px before the footer actions. The 44px close target is positioned independently from header flow so it does not inflate the title-to-content spacing.

Operational tables remain tables on compact screens and use native horizontal scrolling when their columns exceed the available inline size. Following the Clerk-style table structure, the shared table uses `border-separate` with zero spacing and paints dividers on individual cells. Conditional 32px light-translucent gradient fades communicate hidden inline content without `backdrop-filter`, so the effect never samples, crosses, or redraws the existing frame border: inline-end appears while content remains ahead, inline-start appears after scrolling away from the origin, and each edge disappears when its boundary is reached. The inherited panel radius clips the fade, edge materials never intercept input or hide the native scrollbar, increased-contrast and reduced-transparency contexts strengthen the surface fade, and reduced-motion contexts remove the opacity transition.

## Components

Reusable primitives are in `src/components/primitives.jsx`: `Button`, `Input`, `SelectField`, `Badge`, `Panel`, `Switch`, and `Icon`.

Switch defaults to the neutral accent tone for generic settings. Use the lighter Apple-style `success-control` green (`#34c759`) track for product availability and active/inactive states so enabled inventory reads as healthy/available without the visual weight of the darker success text token.

Toast feedback uses `sonner` with a single root `Toaster`. Use success toasts for completed cashier actions such as product saves, cart clearing, settings saves, and completed sales. Use error toasts for validation, stock, and payment failures. Barcode scan results stay spatially attached to the scanner and must not also produce a global toast.

Organization bootstrap uses a centered, calm system surface while Clerk prepares the user's first store. Loading copy uses the title `Menyiapkan toko Anda` with `Kami sedang menghubungkan akun Anda ke toko.`; failures use `Toko belum berhasil disiapkan`, a short recovery explanation, leading secondary `Coba lagi`, and quiet ghost `Keluar` actions. Tenant-scoped application content must remain unmounted until Clerk exposes an active organization ID. Reuse the standard app background, surface, border, radius, typography, button, focus, and spacing tokens rather than introducing a separate authentication style. Loading status uses `role="status"` with `aria-busy="true"`; error status uses `role="alert"`.

The global barcode scanner stays open after both successful and unsuccessful scans so cashiers can continue scanning without reopening it. Keep the camera active and clear a submitted manual barcode for the next entry. Camera reads of the same barcode use an explicit 1,000ms acceptance cooldown measured from the last accepted read, so holding one code in frame cannot add quantity faster than once per second while deliberate repeated scans remain predictable; different barcodes may proceed as soon as the current mutation finishes. Start capture with an environment-facing 720p camera preference so mobile browsers choose a useful rear-camera stream without making that constraint mandatory on single-camera devices. Camera startup failures must distinguish denied permission, missing hardware, an in-use camera, and insecure browser contexts in concise Indonesian copy while preserving manual barcode entry. While a detected value is being processed, mark the workspace busy, show a prominent compact processing surface over the camera for at least 180ms, and block overlapping camera or manual submissions without disabling the explicit `Selesai` close action. The scanner header uses that direct text label with a 44px touch target instead of relying on a small icon-only close control. Do not draw a persistent guide box or scan frame over the live camera; the unobstructed feed is the targeting surface. The spinner is functional state feedback, uses only rotation, and becomes static under reduced motion.

Scan completion uses one scanner-local confirmation material above the bottom controls, never a global toast. The surface is translucent near-black with strong backdrop blur, a subtle light border and shadow, and an 18px continuous-feeling corner radius. A compact indicator at inline-start carries the icon: light green with a check for success, light yellow with a warning mark when the product is unknown or processing fails. A successful cart scan includes the product name, formatted price, resulting cart quantity, and barcode; form-only barcode capture may omit product details because it has not resolved a catalog product. The message and product information stay white, while metadata uses secondary white. The confirmation enters over 180ms with a small upward translation and opacity using the strong shared ease-out curve, remains readable briefly, then exits over 140ms along the same path. It is always mounted through its exit so content does not disappear before the material. Rapid results retarget the CSS transition rather than restarting a keyframe. Reduced motion removes translation and keeps a 140ms cross-fade; reduced transparency replaces the glass with an almost-solid dark surface; increased contrast strengthens its border. On success, the visual confirmation and subtle synthesized tone begin on the same completion event. Sound never replaces the visual, is disabled when reduced motion is requested, and can be turned off immediately through the local `Bunyi pemindaian` preference in Pengaturan without changing store data. The scanner closes only through its explicit close control except after the product-form confirmation has remained visible long enough to register. It is a dedicated full-screen scan workspace, not a modal card: the live camera feed should own the entire viewport edge to edge without a persistent targeting rectangle, and anchor title, close action, errors, result confirmation, and manual-entry controls in top and bottom gradients.

Buttons support primary, secondary, ghost, danger, disabled, and icon usage. Primary marks the single forward or commit action in a local region, including checkout, barcode entry, add/create, save, and apply. Use at most one primary action per toolbar, dialog, or action cluster. Filters, navigation, cancel/close, retry, table-row actions, and destructive actions keep their secondary, ghost, or danger hierarchy.

Cards and panels use tokenized borders, radii, shadows, and background colors. POS product cards use an open, image-first composition rather than a bordered panel: a clean square photo with `panel` radius and no stock badge, a white circular plus control over the bottom-right, a product name clamped to two lines, and a bold IDR price directly below. The visible add surface is 36px inside a 44px touch target, uses a 20px plus icon, and retains an accessible name that says `Tambah` plus the product name. Product-card prices omit the repeated `Rp` prefix. The text aligns directly with the image edge, and the card has no footer, divider, outer border, background, or shadow.

Showcase modules consume production components; production pages never import showcase modules. Keep behavioral variants explicit, such as `ProductCard` and `PosProductCard`, instead of combining unrelated modes through boolean props. This keeps design-system examples representative without coupling runtime screens to demonstration code.

Forms use visible labels, muted placeholder text, and focus outlines from the `focus` token. Standard `Input`, `SelectField`, and search surfaces and hit areas are 44px at every viewport width; `Input size="large"` is 48px. Text fields use a 1px focus outline plus the stronger border token; keyboard focus on buttons and other discrete controls remains 2px for accessibility. Validation stays inline beside the affected field with a danger border and concise error text; do not make cashiers infer an invalid field from a toast alone. Product prices must be at least `Rp1`. Use thousand separators for product price and stock inputs while sending plain numeric values to the API. Use the controlled floating `SelectField` popover for finite option sets such as product category, not a native select. Header-level `SelectField` controls may hide the visual label with an accessible sr-only label so compact page headers keep one aligned control row. Product numeric fields use two columns at most: Price and Stock share one row, while Unit spans the full row beneath them.

Cash payment input accepts only finite, non-negative amounts and completes checkout only when the amount covers the grand total. Associate validation copy with its field through `aria-describedby` and expose invalid state with `aria-invalid`. Selected category and payment controls expose `aria-pressed`; dynamic add, update, and change feedback uses a polite live region. Motion-only status cues must stop under reduced-motion preferences.

Search fields must keep typing immediate while debouncing expensive filtering or API work by roughly 220ms. Apply this to POS product search, catalog search, transaction search, stock movement search, and searchable pickers so cashier feedback stays direct without sending unnecessary queries.

Long operational product catalogs isolate their render work with a memoized catalog boundary, defer local filter computation while typing, and apply `content-visibility: auto` with an intrinsic card size. Keep callbacks and collection props stable so unrelated cart-payment input does not rerender the complete product grid.

## Layout

POS product-card add controls keep a 36px visible circle inside a 44px target and use a 20px plus glyph with a 3px rounded stroke. The floating cart trigger uses a 1rem base clearance above the shared navigation clearance before its scroll-responsive translation.

The authenticated app keeps one smartphone-first shell at every viewport width.
