# Design System

### Product photos

Product forms use one controlled photo field with a visible label and one large, pale upload area with a dashed border, centered camera icon, direct instruction, and JPG/PNG/WebP helper text. The complete area is the upload target; after selection, preview, filename, replace affordance, and an icon-only remove action remain within that same stable area. Empty and preview states crossfade in that stable frame: the old state exits over 120ms while scaling to `0.98`, and the new state enters over 180ms from the same scale. Reduced-motion contexts retain a 120ms opacity handoff without scale. The field accepts one photo up to 5 MB and the backend automatically compresses it to a maximum stored size of 200 KB. Stored product photos are normalized to JPEG, use a white background for transparent source pixels, and keep their aspect ratio while quality and dimensions are reduced as needed. Do not show a category stock photo before the user chooses an image, and do not add a second filename caption below the field. Product-list rows place an 80px rounded thumbnail at inline-end, opposite the product identity and operational values; images remain decorative when adjacent text already names the product. Category fallback photography is allowed only when a product has no stored image URL. Owned product photos are delivered through the app's first-party `/api/v1/product-images/` route, which reads authenticated R2 objects and returns immutable browser caching; production UI must not depend directly on the rate-limited `r2.dev` development endpoint. If a stored image fails during browser startup, keep a neutral placeholder while retrying the same URL after 500ms, 1.5s, and 3s; never substitute unrelated category photography. Connectivity, page visibility, and mobile browser resume events retry the original stored URL again, using a cache-busting query without changing the persisted URL. A permanently broken stored URL settles on the neutral placeholder. Product-form barcode capture uses a separate, full-width secondary `Pindai barcode` action immediately before the labeled barcode field. The action carries the 20px `scan` icon and remains visually distinct from manual barcode entry, while both controls stay grouped with an 8px gap.

### Master data

Settings uses query-backed navigation for `profile`, `categories`, and `units`. Its workspace keeps the smartphone composition at every width: navigation remains an overflow-safe horizontal tab row and the active surface stays centered with a 48rem maximum width. Tabs and actions keep targets at least 44px tall; long master-data names wrap inside `min-width: 0` identity groups, and item, confirmation, restore, create, and save actions remain stacked and full-width. Selection uses a neutral muted surface and `aria-current="page"`, never the primary action treatment. Do not add a vertical navigation rail or redundant store-summary aside. Settled tab content uses a short direction-aware 20px slide-in that follows `profile → categories → units`; it has no exit delay, remains interruptible, skips the first render, and becomes a brief opacity-only crossfade under reduced motion.

Master-data lists use one primary bordered surface with flat rows and quiet dividers; never wrap each row in another decorative card. Active status is implicit in the main list, while low-frequency rename and archive actions live in one trailing overflow menu. Archiving is reversible and should complete immediately with an `Urungkan` toast rather than expanding a confirmation card; no master-data flow hard-deletes records. Archived items stay behind a compact disclosure row and use the same flat row rhythm at lower emphasis. Inline master-data inputs and the `Tambah`, `Batal`, and `Simpan` button surfaces share an exact 36px visual height; buttons retain 44px hit targets so alignment stays precise without sacrificing touch accessibility. Finite product selectors keep search, selection, and a quiet `Tambah … baru` action inside one anchored popover; activating create replaces the option list with a compact input and secondary text actions. A successful create selects the new item and closes only the popover, while an archived-name match offers `Pulihkan` inline. Current archived values remain visible but cannot be newly assigned, and category/unit lists stay alphabetical. The master-data manager is the primary bordered surface and must not be wrapped in another decorative panel.

## Product Surface

Balanja is a retail point-of-sale surface for Indonesian UMKM shops. The interface should stay simple, dense, quiet, and fast for repeated cashier work: white surfaces, soft borders, compact controls, product-image cards, clear stock signals, and near-black primary checkout actions.

### Brand identity

The favicon is the compact brand mark: an abstract isometric retail volume made from exactly three uninterrupted architectural planes inside an edge-to-edge 32px square with an 8px corner radius. The isometric volume spans 22px horizontally with a 4–5px optical inset so it remains prominent after browser-tab padding is applied. Keep `public/favicon.svg` as the active browser favicon so it remains crisp at tab sizes. The volume contains no door, window, letterform, or text and stays intentionally restrained—no gradient, shadow, border, literal shopping symbol, or fine detail. `favicon-soft.svg` and `favicon-inverse.svg` are approved tonal explorations of the same geometry; variants may change only the neutral plane and background colors, never the silhouette, coordinates, scale, or number of planes. The mark complements the shared `Balanja` wordmark but does not replace it in application headers.

## Tokens

Color tokens live in `src/index.css` through Tailwind v4 `@theme`: `app-bg`, `surface`, `surface-muted`, `border`, `text`, `text-muted`, `accent`, `danger`, `success`, `warning`, and `focus`.

The global `app-bg` canvas is pure white and matches `surface` on every public and authenticated page. Do not use gray page bands or alternate section backgrounds to create hierarchy. Use spacing, typography, complete component borders, and semantic status fills instead. Page headers, local toolbars, navigation chrome, content sections, list rows, and card internals do not use standalone top or bottom divider lines; a complete border may still define an input, card, table, drawer, popover, or dialog.

Where older component descriptions below mention quiet, inset, or cell dividers, interpret that relationship as spacing and alignment only. The divider-free global rule above is authoritative, with two deliberate exceptions: the Products list uses a quiet full-width divider between adjacent rows to keep dense catalog items visually distinct, and the persistent bottom navigation uses one top border to separate fixed chrome from scrolling content.

`text-subtle` remains an accessible neutral rather than low-contrast decoration. Text carrying meaning must meet at least a 4.5:1 contrast ratio at normal sizes; use borders, spacing, or weight—not barely visible gray—to preserve hierarchy.

Typography uses Manrope through `--font-sans` for headings, product names, labels, search, categories, units, status pills, helper copy, and actions. JetBrains Mono through `--font-mono` is a restrained operational-data accent, not a second body face: apply it only to barcodes, prices, stock numbers, totals, deltas, and their editable input values, always with tabular figures where numeric comparison matters. Keep adjacent language such as category names and units in Manrope, and never apply Mono to a complete row, form, drawer, or paragraph. Operational text should stay between 12px and 17px. Small barcodes may use 12px Mono with slight positive tracking; page titles use the established 18px authenticated top-bar treatment.

Spacing follows 4px-based Tailwind steps. Repeated panels use 24px gutters and cards use 12px to 16px internal padding. The smartphone control contract applies at every viewport width: standard buttons are 44px, large primary buttons are 52px, standard inputs and selects are 48px, large inputs are 56px, and search fields are 44px. Compact buttons and fields may keep a 36px visible surface only when their outer interactive area remains at least 44px. Dropdown options keep a fixed 40px visual height. Editable inputs, textareas, and native selects use at least 16px text on coarse touch devices to prevent focus-triggered browser zoom; never disable user pinch-zoom through viewport restrictions.

Radius follows an 8px/16px/32px radius hierarchy so each level remains visually distinct after smoothing: `control` is XS at 8px for compact or utility controls and tags; `card` is S at 16px for inputs, selects, cards, and standard action buttons; `panel` is M at 32px for modals, panels, and drawer top corners. Every non-zero rounded rectangle—including pseudo-elements—uses 60% Apple-style smoothing through the shared `--corner-smoothing` contract and native `corner-shape: superellipse(2.0036)`. The value is the CSS superellipse parameter equivalent of the path generator's 4.01 exponent at smoothing 60. Modal and drawer surfaces are the sole smoothing exception: keep their existing radius and layout, but use the dedicated `--corner-smoothing-overlay: 20%` contract with `corner-shape: superellipse(1.4179)`, equivalent to the path generator's 2.67 exponent. Modal and drawer headers use the shared sticky-header contract so the title and dismissal actions remain visible while only the body content scrolls. Full-radius circles, avatars, pills, progress tracks, and handles retain `corner-shape: round` so their original geometry does not change. Browsers without `corner-shape` support fall back to the existing circular `border-radius` geometry. Do not introduce additional radius tiers unless a component's geometry explicitly requires an exception.

Shadows are reserved for content surfaces: `low` for cards, `panel` for elevated overlays and interior panels, and none for buttons or selected control states. The outer app shell and top bar stay shadow-free; the persistent bottom navigation is the sole chrome exception and uses the restrained upward `--shadow-navigation` token.

Every button follows one Uber-inspired flat system. Primary uses a solid near-black surface with white text; secondary uses a neutral surface and quiet border; ghost uses transparent chrome with text and hover fill; danger uses the semantic soft-red surface. The POS product-card add action is the intentional visual exception: it uses a white circular plus control over the product photo so the repeated action remains compact and spatially attached to the item without adding another strong color. Buttons and selected control states never use gradients, bevels, pseudo-element rings, text shadows, or elevation shadows; the repeated photo-overlay add control alone may use `shadow-low` to remain legible over changing imagery. Hover changes only semantic background or text color. Press feedback scales to `0.97` over the shared interaction duration, keyboard focus retains the two-pixel focus outline, disabled controls retain reduced opacity, and reduced-motion contexts remove the transform.

Motion uses `--duration-fast`, `--duration-base`, and `--ease-standard`. Keep transitions short and functional. Transition only explicit, compositor-friendly properties such as transform and opacity; do not animate box shadows. Gate hover motion behind `(hover: hover) and (pointer: fine)`. Dialogs enter and exit over 200ms with backdrop opacity plus a centered surface scale from `0.98` to `1`; in reduced-motion contexts, remove the scale while retaining the opacity transition. The barcode scanner is not a dialog: it takes over the full viewport and should transition with opacity only, without a floating-card scale or inset reveal. Add-to-cart actions should respond on press and confirm completion with a brief product-card pulse or compact status chip, using transform and opacity so the workflow stays fast. Async form labels may use the shared directional text swap: old text exits upward by 4px over 120ms and new text enters from 4px below over 180ms, while the parent control retains a stable minimum width. Reduced motion keeps only the 120ms opacity handoff.

Anchored popovers use the shared floating portal layer above dialogs and recalculate their viewport position on resize or scroll. They may flip above the source control when vertical room is limited, and must never be clipped by a dialog's scroll container.

Loading skeletons should mirror the final retail layout instead of showing generic bars alone. Use full-page skeletons only before a page has initial data. Once settled content exists, refetches and filter loads preserve the current layout, contrast, and usable controls without a visible badge, pulse, or opacity change. Announce background activity through the shared visually hidden polite status region; surface only errors or explicit mutation progress. Disable controls only for explicit pending mutations such as save, checkout, or destructive confirmation, not for background refetches. For POS surfaces, reveal initial skeleton cards and order-summary blocks with a short 560ms rise-in and a looping horizontal sheen that travels across each placeholder in roughly 1.5s. Apply the same motion language to dashboard cards, catalog tables, transaction lists, and settings forms so every initial data load feels consistent. Keep the shimmer subtle, use surface-muted tones plus a soft white highlight, and disable both the rise and shimmer in reduced-motion contexts. The Settings initial skeleton uses the same compact horizontal navigation and centered 48rem content geometry as the settled page; it never introduces a desktop rail or restores the removed store-summary aside.

Operational tables on Produk, Stok, and Transaksi begin directly with the column-header row inside their bordered surface; do not add a second card header that repeats the page title or explains sorting. Keep search, filters, and creation actions in the page toolbar; background updating status stays visually hidden. Header labels and body values share the same horizontal cell inset, including sortable headers, so every column starts or ends on one consistent alignment line. The table wrapper has no horizontal padding: header and row separators must run edge to edge across the bordered surface on all three pages.

The Produk page keeps sorting, category, and status controls together inside its icon-only Vaul bottom drawer; do not add a separate sort icon. The search toolbar contains only search and the product-creation action, and it does not render a persistent category-pill row beneath it. The drawer presents `Urutkan` first, followed by category and status. Sort choices use direct task labels rather than a separate field-and-direction pair: newest, oldest, name A–Z/Z–A, lowest/highest stock, and lowest/highest price. `Terbaru ditambahkan` is the default. Drawer selections remain local drafts until `Terapkan` commits all three controls in one update and closes the sheet. Closing through X, scrim, Escape, or swipe discards drafts; reopening restores the last applied values. `Atur ulang` resets only the drafts to default and still requires `Terapkan`, while page search remains live and debounced. Its header contains only the `Filter produk` title and close action, without subtitle copy. Match the product modal optically: use 24px surface insets and title-to-content separation, 16px between filter groups, 8px between each field label and its options, and 24px before the footer actions. The 44px close target is positioned independently from header flow so it does not inflate the title-to-content spacing.

Operational tables remain tables on compact screens and use native horizontal scrolling when their columns exceed the available inline size. Following the Clerk-style table structure, the shared table uses `border-separate` with zero spacing and paints dividers on individual cells. Conditional 32px light-translucent gradient fades communicate hidden inline content without `backdrop-filter`, so the effect never samples, crosses, or redraws the existing frame border: inline-end appears while content remains ahead, inline-start appears after scrolling away from the origin, and each edge disappears when its boundary is reached. The inherited panel radius clips the fade, edge materials never intercept input or hide the native scrollbar, increased-contrast and reduced-transparency contexts strengthen the surface fade, and reduced-motion contexts remove the opacity transition.

## Components

Reusable primitives are in `src/components/primitives.jsx`: `Button`, `Input`, `SelectField`, `Badge`, `Panel`, `Switch`, and `Icon`.

Switch defaults to the neutral accent tone for generic settings. Use the lighter Apple-style `success-control` green (`#34c759`) track for product availability and active/inactive states so enabled inventory reads as healthy/available without the visual weight of the darker success text token.

Toast feedback uses `sonner` with a single root `Toaster`. Use success toasts for completed cashier actions such as product saves, cart clearing, settings saves, and completed sales. Use error toasts for validation, stock, and payment failures. Barcode scan results stay spatially attached to the scanner and must not also produce a global toast.

Organization bootstrap uses a centered, calm system surface while Clerk prepares the user's first store. Loading copy uses the title `Menyiapkan toko Anda` with `Kami sedang menghubungkan akun Anda ke toko.`; failures use `Toko belum berhasil disiapkan`, a short recovery explanation, leading secondary `Coba lagi`, and quiet ghost `Keluar` actions. Tenant-scoped application content must remain unmounted until Clerk exposes an active organization ID. Reuse the standard app background, surface, border, radius, typography, button, focus, and spacing tokens rather than introducing a separate authentication style. Loading status uses `role="status"` with `aria-busy="true"`; error status uses `role="alert"`.

The global barcode scanner stays open after both successful and unsuccessful scans so cashiers can continue scanning without reopening it. Keep the camera active and clear a submitted manual barcode for the next entry. Camera reads of the same barcode use an explicit 1,000ms acceptance cooldown measured from the last accepted read, so holding one code in frame cannot add quantity faster than once per second while deliberate repeated scans remain predictable; different barcodes may proceed as soon as the current mutation finishes. Start capture with an environment-facing 720p camera preference so mobile browsers choose a useful rear-camera stream without making that constraint mandatory on single-camera devices. Camera startup failures must distinguish denied permission, missing hardware, an in-use camera, and insecure browser contexts in concise Indonesian copy while preserving manual barcode entry. While a detected value is being processed, mark the workspace busy, show a prominent compact processing surface over the camera for at least 180ms, and block overlapping camera or manual submissions without disabling the explicit `Selesai` close action. The scanner header uses that direct text label with a 44px touch target instead of relying on a small icon-only close control. Do not draw a persistent guide box or scan frame over the live camera; the unobstructed feed is the targeting surface. The spinner is functional state feedback, uses only rotation, and becomes static under reduced motion.

Scan completion uses one scanner-local confirmation material above the bottom controls, never a global toast. The surface is translucent near-black with strong backdrop blur, a subtle light border and shadow, and an 18px continuous-feeling corner radius. A compact indicator at inline-start carries the icon: light green with a check for success, light yellow with a warning mark when the product is unknown or processing fails. A successful cart scan includes the product name, formatted price, resulting cart quantity, and barcode; form-only barcode capture may omit product details because it has not resolved a catalog product. The message and product information stay white, while metadata uses secondary white. The confirmation enters over 180ms with a small upward translation and opacity using the strong shared ease-out curve, remains readable briefly, then exits over 140ms along the same path. It is always mounted through its exit so content does not disappear before the material. Rapid results retarget the CSS transition rather than restarting a keyframe. Reduced motion removes translation and keeps a 140ms cross-fade; reduced transparency replaces the glass with an almost-solid dark surface; increased contrast strengthens its border. On success, the visual confirmation and subtle synthesized tone begin on the same completion event. Sound never replaces the visual, is disabled when reduced motion is requested, and can be turned off immediately through the local `Bunyi pemindaian` preference in Pengaturan without changing store data. The scanner closes only through its explicit close control except after the product-form confirmation has remained visible long enough to register. It is a dedicated full-screen scan workspace, not a modal card: the live camera feed should own the entire viewport edge to edge without a persistent targeting rectangle, and anchor title, close action, errors, result confirmation, and manual-entry controls in top and bottom gradients.

Buttons support primary, secondary, ghost, danger, disabled, and icon usage. Primary marks the single forward or commit action in a local region, including checkout, barcode entry, add/create, save, and apply. Use at most one primary action per toolbar, dialog, or action cluster. Filters, navigation, cancel/close, retry, table-row actions, and destructive actions keep their secondary, ghost, or danger hierarchy.

Cards and panels use tokenized borders, radii, shadows, and background colors. POS product cards use an open, image-first composition rather than a bordered panel: a clean square photo with `panel` radius and no stock badge, a white circular plus control over the bottom-right, a product name clamped to two lines, and a bold IDR price directly below. The visible add surface is 36px inside a 44px touch target, uses a 20px plus icon, and retains an accessible name that says `Tambah` plus the product name. Product-card prices omit the repeated `Rp` prefix. The text aligns directly with the image edge, and the card has no footer, divider, outer border, background, or shadow.

Showcase modules consume production components; production pages never import showcase modules. Keep behavioral variants explicit, such as `ProductCard` and `PosProductCard`, instead of combining unrelated modes through boolean props. This keeps design-system examples representative without coupling runtime screens to demonstration code.

Forms use visible labels, muted placeholder text, and focus outlines from the `focus` token. On mobile, standard `Input` and `SelectField` controls are 48px; `Input size="large"` is 56px; and search controls are 44px. An explicitly compact form control may use a 36px visual surface inside a 44px hit area. Text fields use a 1px focus outline plus the stronger border token; keyboard focus on buttons and other discrete controls remains 2px for accessibility. Validation stays inline beside the affected field with a danger border and concise error text; do not make cashiers infer an invalid field from a toast alone. Product prices must be at least `Rp1`. Use thousand separators for product price and stock inputs while sending plain numeric values to the API. Use the controlled floating `SelectField` popover for finite option sets such as product category, not a native select. Header-level `SelectField` controls may hide the visual label with an accessible sr-only label so compact page headers keep one aligned control row. Product numeric fields use two columns at most: Price and Stock share one row, while Unit spans the full row beneath them.

Cash payment input accepts only finite, non-negative amounts and completes checkout only when the amount covers the grand total. Associate validation copy with its field through `aria-describedby` and expose invalid state with `aria-invalid`. Selected category and payment controls expose `aria-pressed`; dynamic add, update, and change feedback uses a polite live region. Motion-only status cues must stop under reduced-motion preferences.

Search fields must keep typing immediate while debouncing expensive filtering or API work by roughly 220ms. Apply this to POS product search, catalog search, transaction search, stock movement search, and searchable pickers so cashier feedback stays direct without sending unnecessary queries.

Long operational product catalogs isolate their render work with a memoized catalog boundary, defer local filter computation while typing, and apply `content-visibility: auto` with an intrinsic card size. Keep callbacks and collection props stable so unrelated cart-payment input does not rerender the complete product grid.

## Layout

The authenticated app keeps one smartphone-first shell at every viewport width. The canvas is full-bleed at compact widths, centered on larger screens, and capped at 1200px; surrounding space uses `app-bg`. Do not introduce a desktop sidebar, outer shell inset, inter-panel gap, or breakpoint-specific shell border and radius. The white top bar and translucent five-item bottom navigation are always present and own the top and bottom safe-area insets. The top bar uses the standard `surface` and `border` tokens rather than an accent fill so the module title, account access, and page content share one quiet hierarchy. The outer shell and top bar stay shadow-free; reserve the larger `panel` radius and `panel` shadow for elevated overlays and interior tool surfaces, while the bottom navigation uses only its dedicated restrained upward shadow. While AppShell is mounted, document scrolling is locked on `html` and `body`; authenticated destinations own vertical movement through a bounded internal scroller, and the lock is removed when the shell unmounts. This prevents body-level portals and annotation overlays from extending the document into blank space. The POS catalog owns the page's single vertical scroller while the cart remains an independent overlay drawer whose item region scrolls between a fixed header and checkout footer. Use the shared Heroicons adapter for every product UI icon; the Produk route uses a tag icon while Stok uses an archive-box icon.

The cart opens horizontally as an overlay drawer from a centered floating pill immediately above the bottom navigation. Animate scale on an inner control so the outer wrapper can retain its centering transform. In reduced-motion contexts, keep the trigger at full scale and use only a brief 140ms fade. It is full-width through 639px and capped at 420px on wider canvases. The floating trigger uses the cart icon, explicit `Keranjang` label, and item count, while the catalog reserves enough bottom space that the trigger never covers the final product row. Modal semantics, focus trapping, and catalog inertness remain active whenever the drawer is present. The drawer uses a text `Tutup` action instead of a duplicate chevron. Keep the scrim mounted through the exit transition, move focus into the drawer, trap focus while open while excluding mounted `inert` descendants, and return focus to the floating trigger after closing. A stacked confirmation dialog owns Escape before the cart so one key press dismisses exactly one spatial layer. Escape, scrim press, and a rightward header swipe may dismiss the drawer. Swipe handling uses pointer capture, a short position history, projected momentum, two-sided rubber-band resistance, and an interruptible spring that starts from the live presentation transform and inherits release velocity; a drawer returning or closing can be grabbed and reversed without jumping. Reduced-motion contexts cross-fade the drawer and scrim without spatial dragging. Preserve compact 36px visual surfaces with 44px targets. The infrequent destructive `Kosongkan keranjang` action lives in one header overflow menu beside the item count, consistently before `Tutup`; it never appears as a full-width peer beneath the primary checkout action. ### Navigation and entry points

Dashboard is the stable authenticated home: signed-in `/` and unknown authenticated paths resolve to `/dashboard`. The cashier workspace remains at `/pos` and uses the direct Indonesian label `Kasir` rather than the technical abbreviation `POS`.

Public navigation renders the shared `Logo` component. The authenticated top bar instead owns the single visible page heading: `Balanja` on Beranda, then `Kasir`, `Produk`, `Stok`, `Transaksi`, `Laporan Penjualan`, or `Pengaturan` on the matching route. Use the same 18px extra-bold Manrope treatment for these route titles. Do not repeat the module name in a local page header beneath the top bar.

Operational navigation uses one persistent five-item bottom navigation at every width: Beranda, Kasir, Produk, Stok, and Lainnya. Lainnya reveals only Transaksi and Laporan Penjualan in a compact anchored sheet so all authenticated routes remain discoverable without squeezing six labels into the bar. Pengaturan lives inside the account popover rather than competing with daily destinations. Navigation selection uses `accent-soft` behind the active icon plus accent text, never the primary action surface reserved for the single forward or commit action in its local region.

The authenticated account trigger lives in the top bar. Its 44px semantic button is visually transparent: render the avatar itself without a border, fill, hover container, or selected wrapper surface. Account avatars use the shared four-color violet, pink, yellow, and cyan `--shadow-avatar` glow; do not substitute a generic neutral shadow. The account popover repeats identity, exposes Pengaturan as a neutral action, then separates Keluar below it with danger styling.
